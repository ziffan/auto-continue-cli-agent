## 1. Ringkasan eksekutif

Fondasi proyek **kuat**: disiplin docs-first nyata (ADR lengkap ter-lock, GOTCHAS/ISSUES hidup), engine
murni-injectable dan bertes, security posture (egress allowlist, injection firewall struktural, PII
allowlist parser, append-only events, no hard delete) **di atas rata-rata** untuk fase ini.

**Namun loop auto-continue — nilai inti produk — belum benar end-to-end.** Audit menemukan **4 temuan P1**
yang semuanya berada di jalur resume/continue dan **tidak tertangkap 308 test** karena test men-stub seam
yang justru mengandung cacatnya (satu test malah meng-encode bug sebagai ekspektasi). Klaim "loop
auto-continue penuh selesai & bertes" di CONTEXT/CLAUDE.md **overstated**: yang terbukti live adalah
inject-continue ke proses proxy dan spawn wrapper baru — bukan resume percakapan CLI nyata.

**Rekomendasi arah:** JANGAN mulai M-remote dulu. Tutup A-1..A-4 (di bawah) sebagai slice "M3e — koreksi loop" terlebih dahulu, karena M-remote tier B (`resume-now <id>`) akan meng-expose jalur resume yang saat ini rusak ke permukaan remote, dan I-15 (live-verify limit asli) akan **pasti gagal** pada temuan A-1.

Verdict per area:

| Area                              | Nilai                    | Catatan                                                         |
| --------------------------------- | ------------------------ | --------------------------------------------------------------- |
| Dokumentasi & decision discipline | Baik sekali              | Drift kecil (§4)                                                |

## 2. Temuan P1 — blocker sebelum fase berikutnya

### A-1 — Resume-by-id memakai ID YANG SALAH; `cli_session_id` tak pernah ditulis di mana pun

**Bukti.**

- `supervisor.ts:241` — `adapter.resumeCmd(session.id, session.cwd)` → meneruskan **id supervisor**
  (4-char base32, `shared/ids.ts`).
- `claude.ts:32-34` → `claude --resume <sessionId>`; `antigravity.ts:103-105` → `agy --conversation <sessionId>`.
- `cli_session_id` hanya muncul di schema/tipe/input `createSession` — **tak ada satu pun jalur kode yang
  mengisinya** (grep seluruh `src/`: 0 penulis). DATA-MODEL.md eksplisit: `cli_session_id` = "id sesi milik
  CLI → `claude --resume <id>`".
- `test/supervisor-dispatch.test.ts:278` malah meng-assert `args == ['--resume', 's-resume-exited-ok']`
  (id supervisor) — **test meng-encode bug sebagai ekspektasi**.

**Dampak.** `claude --resume <acca-id>` / `agy --conversation <acca-id>` akan ditolak CLI nyata → **seluruh jalur resume-by-id (ADR-014 §3, US-3, AC-3) gagal 100% di dunia nyata**. Ini lebih buruk dari sekadar "belum live-verified" (I-15): secara struktural tak ada sumber ID yang benar.

**Remedi (Tier-1, slice sendiri).**

1. Tangkap id sesi CLI saat wrapper jalan:
   - CC: hook `SessionStart` (payload memuat session id; transport hook = A-5) **atau** korelasi transcript
     `~/.claude/projects/<cwd-encoded>/<uuid>.jsonl` (file termuda pasca-spawn; fakta path sudah di
     RESEARCH/CLAUDE.md §7).
   - agy: perintah resume yang auto-printed saat exit (fakta CONTEXT 2 Jul) + `~/.gemini/` conversations dir.
2. Tulis via method repo baru `sessions.setCliSessionId(id, cliId)`.
3. `realDispatch` cabang `exited`: `session.cli_session_id` absen → **BLOCKED + notif** (bukan spawn dengan
   id salah), else `resumeCmd(session.cli_session_id, cwd)`.
4. Perbaiki assertion test + tambah test "cli_session_id NULL → BLOCKED".

### A-2 — Spawn-gagal di resume-by-id = unhandled rejection → daemon CRASH

**Bukti.** `process-wrapper.ts:102` — jalur spawn-gagal `runSession` me-return
`waitForExit: Promise.reject(err)` (tidak throw). `supervisor.ts:110-119` — default `spawnResumeFn` men-destructure hanya `sessionId` dan **membuang `waitForExit`** → rejected promise tak pernah di-handle → `unhandledRejection` → proses daemon **mati** (Node ≥15 default throw). Komentar di `supervisor.ts:243-244`
("spawnResumeFn melempar → ditangkap catch luar") **salah** untuk implementasi default — catch luar tak pernah tersentuh.

Skenario nyata: daemon jalan sebagai service (M5) dengan PATH minimal → `which('claude')` null → sesi baru FAILED (benar) tapi **daemon ikut mati**; lebih buruk lagi, `markResumed` di `supervisor.ts:246` terlanjur menandai sesi lama RESUMED padahal resume gagal.

**Remedi (Tier-1, kecil).** Di default `spawnResumeFn`: tangkap hasil — `result.waitForExit.catch(err => events.append({type:'resume_spawn_failed', ...}))`; dan **jangan** `markResumed` bila sesi baru langsung FAILED (cek status sesi baru atau kembalikan flag gagal dari `runSession`). Tambah test: spawnResume default + binary tak ada → daemon tetap hidup + event tercatat.

### A-3 — Auto-continue hanya bekerja SEKALI per sesi hidup (siklus limit kedua tak terdeteksi)

**Bukti rantai.**

1. `limit-watcher.ts:37,45` — `latched` permanen per instance; setelah limit pertama, sinyal berikutnya tak pernah diklasifikasi lagi.
2. `sessions.ts:95-104` — `markLimitHit` guard `WHERE status='RUNNING'`; setelah inject sukses status = `RESUMED` (`markResumed`), **tak ada transisi RESUMED→RUNNING** di mana pun.
3. `supervisor.ts:290` — usage-monitor `listRunning` filter `status==='RUNNING'` → sesi RESUMED yang masih hidup & aktif **berhenti dipantau** proximity/cache.

Konsekuensi: flow PROJECT §4 langkah 10 ("Status = RESUMED … Kembali ke 3") **tidak terjadi**. Sesi panjang yang kena limit 2× (persis persona target: sesi harian menabrak window 5-jam berulang) hanya ter-rescue sekali; limit kedua lewat senyap. Tak ada test yang mencakup siklus kedua.

**Remedi (Tier-1, state machine).**

1. Definisikan transisi RESUMED→RUNNING: paling sederhana, wrapper menandai kembali RUNNING saat inject diterima (handler inject sukses → `sessions.markRunning(id)`), atau saat output baru mengalir pasca-inject.
2. Un-latch limit-watcher saat inject sukses (wrapper tahu momen ini — `createInjectHandler` bisa diberi callback `onInjected` → `watcher.reset()`).
3. Sertakan `RESUMED`+alive di `listRunning` monitor (atau setelah #1, tak perlu).
4. Test siklus penuh: limit → inject → RUNNING → limit kedua → terdeteksi lagi.

### A-4 — agy resume-by-id sesi MATI mustahil: probe butuh LS hidup, opsi #3 ADR-010 belum ada

**Bukti.** `realDispatch` job `probe` memanggil `adapter.probeUsage({sessionPid: session.pid})` (`supervisor.ts:147`). Untuk agy (`antigravity.ts:44-57`), probe **wajib** `sessionPid` dengan LS hidup — pada sesi `exited` PID sudah mati → `discoverLocalPorts` kosong → throw → `'retry'` → backoff cap 60 menit
**selamanya**, tanpa pernah surface ke user sebagai kondisi buntu. Jalur pre-resume standalone (`retrieveUserQuota` OAuth, ADR-010 opsi #2 pasangan #3) **belum diimplementasi** — dan G-1 mencatat token on-disk stale → butuh refresh via `oauth2.googleapis.com` (egress di luar whitelist NFR saat ini).

**Dampak.** Sesi agy yang mati saat limit (reboot, crash, terminal tertutup) **tak akan pernah auto-resume**; job probe menumpuk retry senyap.

**Remedi.**

- Keputusan user diperlukan (pending decision baru): implement opsi #3 + tambah `oauth2.googleapis.com` ke whitelist NFR (ADR baru — men-supersede scope egress), ATAU fallback fresh-launch snapshot, ATAU terima batasan "agy exited = manual" secara eksplisit.
- Minimal (tanpa keputusan): dispatch mendeteksi kondisi "probe impossible" (agy + proc_state=exited) → event + notif `PROBE_IMPOSSIBLE` + stop retry (surface manual), jangan retry-loop senyap selamanya.

## 3. Temuan P2

### A-5 — Deteksi limit CC PRIMER (hook `StopFailure`) belum diimplementasi & tak dilacak issue

ADR-001/CLAUDE.md §7 menetapkan hook `StopFailure` matcher `rate_limit` sebagai **jalur deteksi primer**; yang terpasang hanya fallback pola output (`limit-watcher.ts:10-11`: "Transport hook … slice terpisah (masa depan)"). `feedSignal` sudah ada tapi **nol pemanggil produksi**. CONTEXT lama menargetkan "hook terpasang (M3d)" — M3d ditutup tanpa itu dan **tak ada issue terbuka** yang melacaknya (I-15 hanya mencakup live-verify). Risiko: wording pesan limit berubah antar versi CC → false-negative; hook = typed & resmi.
**Remedi:** buka issue (P2), slice: tulis settings hooks (`CLAUDE_CONFIG_DIR`/`--settings`) + kanal callback (reuse socket kontrol per-sesi) → `watcher.feedSignal({type:'stopfailure', error})`. Sekalian menjadi sumber
`cli_session_id` untuk A-1 (payload `SessionStart`).

### A-6 — `acca status` tak menampilkan `reset_at` terjadwal & liveness daemon → AC-4 belum benar-benar lulus

Kolom tabel (`status.ts:8`): `#id tool status proc pid cwd updated` — **tanpa reset_at/reset_source**,
padahal AC-4 (PROJECT §6) = "usage + sesi + **reset terjadwal**" dan wireframe §5 menampilkan `LIMIT_HIT → resume 03:15 WIB`. `meta.getHeartbeat()` ada (`meta.ts:29`) tapi **tak pernah dibaca** `status` — NFR Observability minta liveness daemon. MILESTONES menandai AC-4 ✅ → **overclaim**.
**Remedi:** tambah kolom `reset` (format `HH:MM (exact|~heuristic|~backoff)`) + baris header `daemon: hidup (pid N, heartbeat Xs lalu) | mati`; koreksi klaim AC-4 di MILESTONES/CONTEXT sampai slice ini masuk.

### A-7 — Gate resume `every(usedFraction < 1)` terlalu ketat untuk CC

`supervisor.ts:160` memblokir resume bila **satu** limit mana pun exhausted. Respons `api/oauth/usage` memuat `limits[]` kaya (weekly_scoped per-model, `is_active`). Model scoped yang tak dipakai sesi (mis. weekly Opus habis, sesi jalan di Sonnet) akan **memblokir resume selamanya** (retry 60m loop). Untuk agy semantik `every` justru benar (dual-limit per grup — G-31).
**Remedi:** per-tool policy di adapter (bukan supervisor): CC → pertimbangkan hanya `five_hour`/`seven_day` global + `is_active`; agy → semua bucket. Pindahkan keputusan "available" ke `adapter` (mis. `isUsageAvailable(snapshot)`) supaya supervisor tak menebak semantik lintas-tool.

### A-8 — Asumsi ACL named pipe Windows belum diverifikasi (ADR-015 "ACL default owner")

Named pipe Node/libuv secara default **bisa di-connect proses user lain** di mesin yang sama (DACL default tidak owner-only seperti chmod 0600). Permukaan: `\\.\pipe\acca-daemon` (`ping/status/rearm`) + `\\.\pipe\acca-session-<id>` (`inject`). Dampak dibatasi desain (inject = token literal tanpa payload;
rearm idempotent), tapi `status` **membocorkan daftar cwd** ke user lokal lain, dan inject bisa dipicu pihak lokal tak sah. Single-user desktop = risiko rendah; node headless multi-akun (ADR-007) = relevan.
**Remedi:** verifikasi DACL nyata saat M5 security pass; bila terbuka, catat sebagai residual risk eksplisit di THREAT-MODEL (local attacker) atau tambah cek `pipe client PID → same session user`.

### A-9 — `genSessionId` 4-char (≈1,05 jt kombinasi) tanpa retry-on-collision + retensi never-purge

`ids.ts` — random tanpa cek unik; PK collision → `createSession` throw → `acca run` gagal misterius.
Dengan retensi tak terbatas (keputusan 5 Jul), probabilitas tabrakan naik terus (birthday: ~50% di ~1.200 baris sesi). **Remedi kecil:** retry loop (≤3×) saat `SQLITE_CONSTRAINT_PRIMARYKEY`, atau naikkan panjang id.

## 5. Hal yang sudah BENAR (dipertahankan)

- **Egress guard** (`shared/http.ts`): allowlist sempit + insecure-TLS dikurung ketat loopback (G-25). Solid.
- **Injection firewall struktural** (`inject-continue.ts`): token hardcoded wrapper, perintah tanpa payload,
  args diabaikan — properti struktur, bukan konvensi. Sesuai ADR-008/013.
- **PII firewall** konsisten di semua permukaan output: parser allowlist (`usage.ts`), notifier (body hanya
  field terkontrol), `acca log` (SUMMARY_ALLOWLIST), `acca status` (scope tak dirender).
- **Credentials**: dibaca saja, error message tak pernah memuat token (`credentials.ts`).
- **IPC**: stale-socket connect-probe (G-14) benar; per-request isolation; 0600 POSIX.
- **Store**: parameterized queries semua; append-only events ditegakkan (tak ada UPDATE/DELETE); migrasi
  forward-only bertransaksi; no hard delete.
- **DST fix** (`reset-estimator.ts`) benar; backoff cap konsisten NFR.
- Disiplin dokumentasi (ADR immutable, GOTCHAS "jebakan dibayar sekali", ISSUES ditutup dengan solusi) —
  kualitas jarang ditemui; pertahankan.

## 6. Catatan proses (kenapa 4 P1 lolos 308 test)

Pola yang sama di keempatnya: **seam actuation di-stub di test, dan review Tier-1 menilai diff per-slice, bukan semantik lintas-slice.** `spawnResume` selalu di-inject (alasan valid: jangan spawn CLI nyata), maka (a) id yang diteruskan tak pernah diuji terhadap kontrak CLI nyata, (b) perilaku default `spawnResumeFn` tak pernah dieksekusi test. Siklus limit-kedua tak punya test karena tiap slice menguji satu transisi.
**Remedi proses:**

1. Tambah kelas test "kontrak integrasi": assert INVARIAN lintas-slice (id yang dipakai resume ≡
   `cli_session_id`; setiap status punya jalur keluar; setiap retry-loop punya terminal state).
2. Definisi selesai untuk slice actuation = **live smoke dengan CLI nyata di jalur default** (bukan proxy) ATAU eksplisit dicatat sebagai belum-selesai di MILESTONES (jangan ✅ dengan catatan kecil).
3. Saat tier-review: reviewer wajib menanyakan "apa yang di-stub test ini, dan siapa yang menguji stub-nya?"
